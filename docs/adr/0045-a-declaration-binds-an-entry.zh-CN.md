# 0045 — 声明绑定的是一个 entry

> **语言：** [English](0045-a-declaration-binds-an-entry.md)（主）· [中文](0045-a-declaration-binds-an-entry.zh-CN.md)

**状态：** Accepted（2026-10-29，随 prism 渲染器腿一起落地）

## 背景

投递是向某个 **entry** 调用函数体：作业里带 `handler`，远端帧里带 `entry`（被交付的代码要寻址的那个符号）。对编译型函数体来说这只是个标签——宿主手里本来就握着闭包，名字是装饰。脚本函数体不同：它的常驻会话按名字逐事件调用，而载体唯一的绑定形式就是声明。而那份声明（`interface_schema` → `receives`）只带事件和解析方式，别的什么都没有，于是 entry 只能是事件名。

这只在每个事件名同时也是语言能定义的名字时成立。并不是。给面向 UI 的事件加标记的场馆（prism 的 `view:<name>`）会把 `view:add-to-cart` 交给函数体，而脚本定义不出那个函数——那个字符不属于标识符。于是：订阅注册成功，emit 命中路由，队列收到消息，载体被要求调用 `view:add-to-cart`，找不到，然后**一声不响地丢掉作业**。在 prism 的渲染器腿上实测：摊位从未被进入，任何地方都没说为什么。

当前载体里也没有 `@on("view:x")` 那种运行时注册可以依靠：`ctx` 暴露的是 `emit` 和 `store`，schema 里扁平的 `{"on": [...]}` 是一串事件名，不是函数引用。对脚本函数体来说，声明就是注册。

## 决定

**订阅声明要说明它绑定的是什么。** `ReceiveDecl`（以及 `Route`）多带一个可选的第二名字，拼写为 `entry`——远端帧早就在用的那个词：

    receives: { "view:add-to-cart": { "entry": "add_to_cart" } }

不写，则事件名就是 entry——今天所有声明的行为不变。这个绑定要走完整条路（声明 → 路由表，引擎的内省分支和注册表分支都要走 → 实例的订阅元组 → `QueuedJob.handler`），因为停在路由表的事实，就是分发器手里没有的事实。

对编译型函数体什么都没变——它们从不看名字。脚本函数体得到的是它缺的那一样东西：说出一个带标记的事件归属哪个函数。

## 后果

- 一个名字的命名空间可以用来路由，而不必同时是可调用标识符的命名空间：前缀、点号以及其它标记语法不再是分发层的 hazard。
- 标记对摊位的代价正好是声明里多一个键，调用点零代价。
- 通配订阅仍然投递**具体**名字（没有逐条消息的声明可查），所以通配订阅者的函数体必须能按具体名字找到——Rust 函数体免费（它不看这个名字），脚本函数体则要么每个事件一个入口，要么逐事件做精确声明。
- **投递失败不再静默。** 投递接缝原先把应答直接丢弃（`run_job_queued`），所以"函数体调不到"——entry 不存在、载体故障——一点痕迹都不留。现在会观察应答：日志里写明事件名、它试图调用的 entry 和摊位类型，并记入死信环 `DeadReason::DeliveryFailed`，带 `{entry, booth_type, error, payload}`。读取是部署者的事，不是 aura 的事：prism 在 `GET /admin/dead` 提供这个环。
