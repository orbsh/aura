# 0048 — 资源是 venue 的原语

状态：已接受（2026-11-23）

## 背景

数据已经是 venue 的：booth 声明 schema，realm 拥有命名空间，store 持有行。而一次执行在参数之外还需要的东西——要读的仓库、要写进去的桶、临时的目录、要拉的镜像——此前无处安放。每个需要它的 booth 都自己造一遍：gravity 长出了一张资源表，第二个 booth（比如构建流水线）就得再长一张同样的表，外加同样一套 git 处理。

资源不是传输细节。`git`、对象桶、快照仓库、镜像仓库解决的是不同形状的问题，而一次性的 workspace 和它们都不一样：它只为一次执行存在，结束即消失。把它们统一成一个概念的，是它们共有的那部分——一个 owner、一种 mode（可读或可写）、一个版本或一段生命期、执行前必须就绪、执行后要处置。

密钥曾是反对的理由：venue 必须在没有密钥的情况下也能跑。确实如此。没有凭证的 venue，就是需要资源的调用在派发时按名字被拒绝的 venue，其余一切不变。

## 决定

**资源是 aura 的原语。** venue 只拥有三样东西：

1. **声明**。一次 activation 在**跑起来之后**才说要什么——`ctx.resource({op, kind, seq})`，和 `ctx.store` 挂在同一个 ctx 上，因为需要什么数据是脚本自己决定的（effector ADR-0003 §5 早已这么写）。声明不跟着调用走：开跑前就固定的那张表没人能填，而"两种说法指同一件事"就是多出来的一种。realm 从 turn 的信封上盖下 OWNER，activation 自己永远不声明 owner——能声明 owner 的就能借用别人的数据。账号跟着调用走：activation 调用的 booth（mount、子 booth）继承它，因为往节点上派发的是它。
2. **名册**。行在 venue 的 store 里——也就是 owner 数据所在的那一处——用框架自留的号段（ns 36，ADR-0040 的 meta 段；版本在 37、密钥在 38——一个 ns 一张表，
    因为 okm 的结构戳是按 ns 一行，共用号位会让一张表的布局变化替另一张说话）。键是 store 的**有类型键**（一个判别子加一个数字），不是 `owner/kind/seq` 的字节拼法：okm 的键是定宽有类型的字段，只有末段可以是变宽字符串，所以文本的身份部分是**声明字段**，`by_owner` 索引让"我拥有的一切"仍然是一次区间读。行里放固定的部分（`desc`、`mode`、`created_at`、指向当前版本的指针），随 kind 变化的进动态段。版本自成一列行并带 `previous` 链，于是撤销是一次读，不需要索引。
3. **接口**。内置在 realm 里，不是 booth：`resource.register`、`resource.secret`、`resource.material`、`resource.published`。平面（prism）像管理节点和令牌那样管理它。

**密钥也存在 venue 里**，放在任何 booth 都不声明的命名空间——于是 booth 的 store plan 根本寻址不到它。这是结构性的而不是命名约定：隔离来自"没有 schema"，不是来自某条需要人记住的规矩。行里只写它用哪个密钥，值永远不在行里。目前落盘是明文；封一层是 okm 有了相应原语之后的事。

**传输是节点的。** venue 授权一次传输——一个地址和一份一次性凭证，按读、写分别铸造，于是泄露的读凭证发布不了。克隆、取引用、GET/PUT、拉镜像都是执行器的工作，realm 里不该有一行。

## Kind

    git       文件树，持久，版本是 branch@sha
    volume    文件树，持久或随 activation 存活
    s3        整块对象，持久；不按前缀扫——资源是被指认的，不是被检索的
    rustic    快照流，持久
    image     registry 里的不可变整块，持久

不需要这些的执行什么都不声明，这是正常的，不是错误。

**一次性资源（workspace）不进名册。** 它们只出现在声明里，序号由 realm 在 activation 内分配，目录由执行器创建并删除。一个活得比执行还长的名字，会对它说出不实的话。

## 影响

- gravity 的资源表从这块能力的主人变成它的客户；它的 `material`/`published` 退化成调用。第二个 booth 拿到同样的服务，不碰 git、s3 或 store。
- venue 知道怎么**授权**一次传输，对怎么执行它一无所知。`kind` 保持身份语义（同一个仓库用 git 交付和用快照交付是两个资源），新 kind 以自己的行和自己的节点适配器出现，而不是新开一根轴。
- 没有凭证的 venue 照样启动，照样运行所有不声明资源的调用：拒绝发生在声明处、按名字、在调用之前，而不是传输到一半才发现。
- owner 从 turn 推导，所以执行器不能靠自称拿到别人的资源：平面从它派发出去的那次调用上解析。
