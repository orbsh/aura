# 0050 — realm 是一行记录：key 里放 id，表里放名字

> **语言：** [English](0050-a-realm-is-a-row.md)（主） · [中文](0050-a-realm-is-a-row.zh-CN.md)

**状态：** 已接受（2026-11-19）。仅取代 ADR-0028 §1 中"realm 以什么标识"这一点；词汇裁决（外层轴叫 realm，其集合叫 realm-set，"ns" 专指 key 段）不变。
**日期：** 2026-11-19

## 背景

realm 就是一个前缀。`MqStore::for_realm(inner, name)` 在每个 key 前后拼 `[u16 BE len][name]`，隔离就是这层绑定：为一个 realm 构造出来的句柄够不到另一个（ADR-0028、`realm_set.rs`）。在 realm 还是部署期词汇的时候，这足够了。一旦 realm 在运行时被创建与销毁 —— 这正是派单级临时 realm 所要求的 —— 它就不够了。

现在的安排有三个问题，而且没有一个是前缀方案本身的 bug：

1. **名字既是身份又是位置。** 改名就要搬走每一个 key；两个 realm 除了名字之外无法区分；而名字有多长取决于谁打字的。
2. **默认 realm 完全没有前缀。** `Engine::new` 用 `Realm::with_mq(mq.clone())` 直接拿共享 engine 句柄，而具名 realm 走 `for_realm(name)`。于是"系统 realm"不是 realm 集合的成员，它是键空间里那一块没有前缀的剩余物。这就是代码读起来像有两层的真正原因。
3. **前缀不是一个对象。** 没有东西能从存储里列举 realm（`RealmSet::live` 列的是内存 map），没有东西能计量它，也没有东西能删除它——"销毁这个 realm"连一个可持有的句柄都没有。

## 决定

**裁决 —— realm 由 ID 标识。id 住在 key 里，名字是表里的一列。持久 realm 与临时 realm 是同一种东西，区别只在于它们那行记录放在哪、以及是否被写过。**

1. **两种形状的 id，一个类型。**

```rust
enum RealmId {
    Persisted(u32),    // 从 realms 表分配，单调递增，永不复用
    Ephemeral(u128),   // uuidv7，进程内铸造，永不进存储
}
```

变体是显式的，不靠宽度推断。宽度是变体的性质，不是它的判别器：uuid 的数值可能落进 `u32` 的范围，而一个把数字而不是字节写出去的序列化器会把这点区别抹掉。让"先在内存表找、再在持久表找"可判定的，是那个标签。

2. **存储前缀是 id，不是名字。** 用 `[u32 BE id]` 取代 `[u16 len][name]`。于是持久 realm 的 key 更短、改名后不变、也不含需要解析才能读懂的编码。临时 realm 从不写入，所以它的 u128 永远不会成为前缀；它只是内存 map 的键，以及日志行能指称的东西。

3. **两张表，一个查找顺序。** `realms`（固定根表：`id → (name, created_at)`）给持久那种；进程内的 map 给临时那种。按 id 解析时先查内存表，再查持久表 —— 临时那种按定义只可能出现在内存里。

4. **只有一种 realm，第一个也不例外。** 默认 realm 变成一个普通的持久 realm，名字为 `main`，它的 key 与其它 realm 一样带前缀。`Engine::new` 那条无前缀的句柄被撤除：没有任何代码路径可以写出不属于任何 realm 的 key。

5. **创建默认只在内存，除非明确要求持久化。** `create` 缺省是 `Ephemeral`；想要持久的调用方自己说。默认选那个不留痕的，是运行时调用的正确偏向。prism 在启动时只创建一个持久 realm（`main`），按名字打开。

6. **临时 realm 完全隔离，而它的类型表是同一套规则换个引擎。** 两种 realm 的注册写的是同样的行 —— `BoothName` 给 ns、`BoothDef` 给定义与 `interface_schema`、`EventRoute` 给订阅 —— 差别只在存储：持久的进 fjall，临时的进它自己的内存。于是类型的 ns 在两边都是 `BOOTH_NS_BASE + id`，一次分配、永不回收，只有一份字典而不是两份。在那里注册的类型只对它自己可见，而那些行随 realm 一起消失，因为整个存储随它消失。

7. **realm 不嵌套。** 临时 realm 不能再创建 realm。job 可以嵌套（effector ADR-0005）—— 那是关于工作的事实，不是关于隔离的 —— 但隔离轴只有一层：很多 realm，没有父子。

## 不做迁移：存储从空开始

没有值得带过去的数据。开发用的存储是旧布局的一次性产物，所以无前缀的那块键空间是被**删除**而不是被重写，新布局从空存储开始，`realms` 表里只有一行（`1 → main`）。

这个选择买到的不只是省下的那个下午。迁移会留下两条必须同步维护的路径 —— 一个懂无前缀 key 的读者和一个不懂的 —— 此后每一次改动都要把两者都保持正确。删掉旧空间意味着从第一个读 id 的提交起，代码只有一条路径，也不存在会慢慢腐坏的兼容模式。

代价要说出来而不是藏起来：那个存储里的东西没了。它是开发存储，没有任何跨重启有意义的东西引用它，而替代方案是一个重写工具 —— 那个工具本身还要对历史上写过的每一张表都正确。

## 后果

- **id 永不复用。** 被销毁 realm 的 id 即使它的行已删除也一并退休；复用一个 id 会让新 realm 继承旧 realm 的数据 —— 读起来像隔离的 bug，其实不是：那是 id 在做它被要求做的事。
- **裸 key 转储不再自解释。** 直接读存储现在需要 `realms` 表才能把 `1` 渲染成 `main`。这是短前缀的代价，在工具里付一次，此后不必每个 key 都付。
- **销毁必须有实义。** 有了行与前缀，`destroy` 是：丢掉活的 Realm（实例、执行器、流、在飞调用）、删除那行、删除前缀范围。临时 realm 的销毁只有第一步：它写的行在它自己的内存里，随它一起消失。
- **`live()` 变成一个查询，而不是列 map。** 答案的持久那一半来自表，临时那一半来自内存。
- **两层读法从代码里消失。** 不存在"系统 realm 加具名 realm"—— 只有 realm 集合，而 `main` 就在里面。
